# shadPS4 on macOS (Apple Silicon): Everybody's Golf

Notes from getting *Everybody's Golf* (CUSA04687, update 01.17) running on a MacBook Pro (Apple M4
Pro, macOS 26.6.2) on 2026-10-14, from a black screen to the opening movie, the island hub and the
tutorial, with sound.

shadPS4 is an x86-64 emulator: the Mac build runs under **Rosetta 2** and executes the game's own
x86 code natively through it. Vulkan is Mesa's **KosmicKrisp** driver on Metal, which the official
release bundles. Every problem below was found on that combination.

## Outcome

| | |
| --- | --- |
| Official 0.20.0 release | Crashes at boot (allocator), then hangs on sign-in, then freezes |
| This fork, game patch, fonts | Boots, title, opening movie, hub, tutorial dialogue, sound, about 30 fps |
| Fork | `github.com/kirbycope/shadPS4`, branch `main`, on top of upstream `c20cc337` |
| Patch file for upstream | `shadps4-macos-fixes.patch` beside this file (`git diff c20cc337 main -- src`) |
| Game patch | `patches/EverybodysGolf.xml`, generated by `patches/make_golf_patch.py` |

Not done yet: nothing known past the tutorial's nickname entry, which is as far as it has been
played. Occlusion queries are emulated as always visible, so predicated draws are drawn rather than
skipped; that costs speed, not correctness.

## Setting up

| | |
| --- | --- |
| Game | `~/Games/PS4/CUSA04687` (base), `~/Games/PS4/CUSA04687-UPDATE` (01.17) |
| DLC | `~/Library/Application Support/shadPS4/addcont/CUSA04687/<one folder per item>` |
| Firmware modules | `~/Library/Application Support/shadPS4/sys_modules` (11.00 set, 436 files) |
| System fonts | `~/Library/Application Support/shadPS4/fonts/font` and `fonts/font2` |
| Game patch | `~/Library/Application Support/shadPS4/patches/kirbycope/EverybodysGolf.xml` plus `files.json` = `{"EverybodysGolf.xml": ["CUSA04687"]}` |
| Config | `~/Library/Application Support/shadPS4/config.json`, `install_dirs` = `~/Games/PS4` |
| Log | `~/Library/Application Support/shadPS4/log/shad_log.txt` |

The packages are fake PKGs, unpacked with `ps4-pkg-tools`: the base into `CUSA04687`, the update
beside it as `CUSA04687-UPDATE` (shadPS4 overlays a `-UPDATE` folder on the base), and each DLC
into its own folder under `addcont`.

**System fonts are not optional.** Without `/sys/common/font` the game draws every runtime string
as nothing: the dialogue bubbles come up empty, and the game waits for a line nobody can read.
shadPS4 says so once at boot, `No dumped system fonts, expect missing text or instability`. The
set used here is archive.org's `sony-ps4-system-font` item, whose `font/` and `font2/` folders map
one to one onto shadPS4's.

## Building

Built on the Command Line Tools with the macOS 26.5 SDK; the 27 SDK's `.tbd` stubs break the CLT
linker (`tapi ... unknown architecture`).

```bash
export SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_OSX_ARCHITECTURES=x86_64 \
      -DENABLE_SYSTEM_VULKAN=ON
cmake --build build
```

The binary is run from the Qt launcher's version folder, next to the official release's
`libvulkan.dylib`, `libvulkan_kosmickrisp.dylib` and `kosmickrisp_mesa_icd.json`, copied from the
release. It needs an rpath to find them, and an ad-hoc signature after that edit:

```bash
V="$HOME/Library/Application Support/shadPS4QtLauncher/versions/kirbycope-main"
cp build/shadps4 "$V/"
install_name_tool -add_rpath @executable_path "$V/shadps4"
codesign -s - -f "$V/shadps4"
```

Without the rpath the build segfaults creating the Vulkan instance.

## The game patch: the Apple GPU carve-out

Under Rosetta the range 0x1000000000-0x6FFFFFFFFF belongs to the GPU and cannot be mapped, so
shadPS4's macOS user range starts at 0x7000000000. The game's allocator hard-codes its heap bases
at 0x10, 0x20 and 0x30 GiB and classifies every pointer by `addr & 0xFFFFFFF000000000`; anything
else gets a null heap, which shows as reads from 0x40 and 0x50 at boot.
`patches/make_golf_patch.py` rewrites every `movabs reg, base` to 0x80, 0x90 and 0xA0 GiB.

One match is not an address. 01.17's `0x14e25cc` is `movabs rax, 0x1000000000` initialising the
sound output table's first entry to `{id 0, format 0x10}`; moved to 0x80 the mixer rejects the
format and renders nothing, and the game is completely silent. The generator excludes it.

The XML also carries **Wait up to 5 seconds for the GPU**: the game declares a GPU hang after one
second (`sceGnmSubmitDone`, `sceGnmDebugHardwareStatus`) and reuses command buffers the GPU is
still reading. First-time shader compiles take longer than that under shadPS4.

## The fixes in the fork

### Boot and save data (`6f06c91c`)

- The sign-in dialog returned OK with shadNet off, and the game waited forever for a user to
  appear. It now reports `USER_CANCELED`, matching the signed-out state `sceNpGetState` reports.
- The game writes saves to `/app0//savedata0` first and falls back to `/savedata0` only on
  `ENOENT`. `open(O_CREAT)` now returns `ENOENT` for a missing parent before the read-only check,
  as FreeBSD does.
- The game's fragment shaders bind more than 64 images; the limit is 128, and a full resource list
  logs and reuses its last slot instead of throwing on the GPU thread.

### Pad speaker ports (`d2683927`)

Games open a pad speaker port per login slot, including empty slots with user -1, and treat the
failure as an unused slot. shadPS4 accepted them, the four ports ran out, and the real user's open
failed. Per-user port types now reject an invalid user.

### Relative VGPR moves (`1e8d400a`)

`v_movrels`/`v_movreld` were a compare-and-select over every VGPR above the base. A few hundred of
them made 56k selects and 2.7 MB of SPIR-V, which Apple's Metal compiler runs out of memory on and
then retries forever. Those VGPRs are now a private array, and a relative move is one indexed load
or store.

### The freeze: Rosetta and write protection (`b123cb78`)

The emulator froze within seconds to minutes: every thread blocked, almost no CPU. stderr had the
answer all along:

```
rosetta error: unexpectedly need to EmulateForward on a synchronous exception
               x86_rip=0x148bd14 ... num_insts=3 inst_index=2
```

`0x148bd14` is a `vmovups ymm` in the game's command buffer writer. Rosetta translates a 256-bit
AVX store into two halves. If another thread write-protects the page between them, the second
half faults after the first has landed, Rosetta cannot unwind it, and the thread never returns. A
small test program reproduces it outside shadPS4: plain stores, `memcpy`, 128-bit stores, shared
memory, alternate signal stacks all survive millions of faults; a 256-bit store from JIT- or
AOT-translated code with a concurrent `mprotect` dies within seconds.

shadPS4 detects CPU writes by write-protecting buffer pages and re-protects them after every
upload, while games keep filling them. On macOS x86-64 the buffer cache now hashes pages instead,
once per GPU submission, including the raw-pointer (DMA) path; `SHADPS4_PROTECT_BUFFERS=1` brings
back protection. Textures stay protected, and any page that faults repeatedly is demoted to the
same content check.

### The opening movie deadlock (same commit)

The GPU waited on a label that a compute queue sets after a dispatch. The game writes a compute
buffer, rings the queue, and rewrites the same buffer for the next frame almost immediately; on
hardware the first has long since run. shadPS4 runs it later on the GPU thread, read the next
frame's contents, and the label the graphics queue was waiting for was never written. The
contents of each compute indirect buffer are now copied when the queue is rung.

### Post-processing atlas over the screen (`c9a57cb8`)

The hub and transitions showed the scene in one quarter, a blur chain in another, black between.
The game samples the top-left corner of its 1920x1080 post-processing target by describing a
960x540 or 480x270 texture at the same address with pitch 1920. The texture cache kept those as
separate images refreshed only through guest memory, so they were stale while the GPU kept writing
the target. A texture binding is now refreshed from a covering GPU-written image at the same
address, pitch, tiling and texel size before use.

### Crash entering the island hub (`d0595dc0`)

`WAIT_ON_CE_COUNTER` called `done()` on the constant engine task's coroutine handle, which is null
for a buffer submitted without a constant engine stream (an indirect buffer). That reads address 0
on the GPU thread. Without a CE task nothing can advance the counter, so there is nothing to wait
for.

### Faces missing or with black lips (`744133a9`)

Avatar faces (Hikari's whole face, Suzuki's lips) were discarded. The face shader saves EXEC into
lanes 1 and 2 of a VGPR with `v_writelane` and restores it with `v_readlane`, and shadPS4's
`ReadLaneEliminationPass` normally folds that back to a scalar. The relative-VGPR array from
`1e8d400a` had moved that register into memory, the fold no longer matched, and a real cross-lane
read of possibly inactive lanes restored EXEC as 0. Registers used with `v_writelane`/`v_readlane`
now stay out of the array.

### SET_PREDICATION

Occlusion queries are emulated with a counter that always reports visible pixels, so ignoring
predication draws exactly what a predicated draw would. It is now logged once instead of per
object.

## Debugging notes

- Driving the game without the screen: with the Mac locked, `screencapture` fails and synthetic
  key presses never reach the window. A small injector in `input_handler.cpp` (a file of
  `cross 300` / `wait 2000` / `shot` lines, read on a thread and pressed into player 1's
  controller; `shot` calls shadPS4's own screenshot) kept testing going, and inputs can never land
  in another application. It is kept out of the fork as a diagnostic patch.
- Finding a draw: skip a per-frame range of draws from a file re-read at every flip and compare
  screenshots; then log the shaders, buffers and textures of the culprit.
- **Read stderr, not only the log.** Rosetta writes its own errors there, and the freeze's cause
  sat in every captured `run.err` for hours before anyone grepped it.
- A thread that is stuck at one instruction in "Rosetta JIT" in a `sample` with no CPU use is
  blocked in the kernel on a fault, not spinning.
- `thread_get_state` on such a thread hangs; in-process tools must not depend on it.
- Write-protecting a page to find its writer does not work for game globals under Rosetta: the
  probe write itself hung the thread. A polling thread did show the sound format going straight
  from 0 to 0x80, never through 0x10, which pointed at a different initialiser: the game patch.
- `sceNgs2SystemRender` being called at all is the first thing to check when a game is silent; a
  wrapper on the LLE library's export (resolved in `Linker::Resolve`) costs ten lines.
